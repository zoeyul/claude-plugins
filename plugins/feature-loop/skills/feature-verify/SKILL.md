# 작업 문서 기준 검증

기능 작업 루프의 마지막 단계다. `feature-spec` 이 정한 검증 표가 작업 목록이다.
**표에 없는 검증을 새로 만들지 않고, 표의 층을 바꾸지 않는다.** 층이 틀렸다고 판단되면
멈추고 문서 수정을 제안한다.

## 전제

- 작업 문서가 있고 승인됐다. 없으면 `feature-spec` 부터 한다
- 구현이 끝났다
- 프로젝트 루트의 `.feature-loop.json` 에서 `appDir`·`testingGuide` 를 읽는다

## 절차

검증 표를 위에서부터 층별로 처리한다. jest 를 먼저 한다 — 빠르고, 여기서 깨지면
화면까지 갈 이유가 없다.

### jest 행

`testingGuide` 가 있으면 그 작성 기준을 따른다.

1. 테스트를 쓴다. 구현이 아니라 사용자가 보는 것(렌더된 트리·콜백·바깥으로 나가는 명령)을 단언한다
2. 프로젝트의 테스트 명령으로 통과를 확인한다
3. **수정 전 코드에서 실패하는지 확인한다.** 새 코드면 지키려는 동작을 하나씩 되돌려
   각각이 테스트를 깨는지 본다. 깨지지 않으면 단언을 다시 짠다. 되돌린 코드는 반드시 원복하고
   `git diff` 로 확인한다
4. **레포에 남길지는 프로젝트의 테스트를 남기는 기준으로 정한다**(기준이 없으면 사용자에게 묻는다).
   남기지 않으면 커밋하지 않고 검증 근거(테스트 이름·결과·되돌려 본 지점)를 PR 에 적는다.
   작업 문서 검증 표에 있다는 이유만으로 남기지 않는다

### maestro 행

조작·실행·테스트 계정은 `verify-screen` 스킬을 따른다. 여기서는 이 스킬에만 있는 것만 정한다.

- 항목 하나에 플로우 하나. 마지막은 `assertVisible`/`assertNotVisible` 로 끝낸다
- 검증 표에 경로가 있는 행(회귀 묶음)은 그 경로에 `tags: [regression]` 을 붙여 커밋한다
- 경로가 `-` 인 행은 임시 디렉터리에 써서 검증만 한다 — 커밋하지 않는다
- 로그인이 필요하면 프로젝트의 로그인 서브플로우(`<appDir>/.maestro/common/`)를 `runFlow` 로 부른다

회귀 묶음 전체는 이렇게 돈다. 연달아 두 번 돌려 둘 다 통과해야 한다(시작 상태를 가정하지 않는지).

```bash
${CLAUDE_PLUGIN_ROOT}/skills/verify-screen/scripts/e2e.sh <appDir> --device <udid> \
  test .maestro --include-tags regression
```

### 실기기 행

자동화하지 않는다. 결과에 "실기기 확인 필요" 로 남기고, 무엇을 봐야 하는지 한 줄로 적는다.

## 결과 반영

1. 작업 문서의 체크박스를 채운다. **통과를 근거로 확인한 항목만** 체크한다
   - jest — 통과 + 수정 전 실패 확인
   - maestro — 마지막 단언까지 통과
   - 실기기 — 체크하지 않는다
2. 보고한다 — 항목별 층·결과·근거(테스트 이름, 플로우 경로, 실패 출력)
3. PR 본문에 작업 문서 링크, 실기기 확인 필요 항목, 결과 요약(`N/N Flows Passed`)을 적는다

작업 문서는 그 기능의 스펙으로 계속 쓰인다. **기능의 요구와 검증 방법만 적는다.** 이번 실행의
사정(테스트 계정 상태, 못 돌린 이유)은 PR 에 적는다. 확인 여부는 체크박스로만 남긴다.

maestro 리포트(`<appDir>/.maestro/reports/`)는 커밋하지 않는다.

실패한 항목은 고쳐서 다시 돌리되, **같은 항목이 두 번 실패하면 멈추고 보고한다.**
접근이 틀렸을 수 있다.

## 하지 않을 것

- `COMPLETED` 만 보고 체크하지 않는다
- 통과만 확인한 jest 테스트로 체크하지 않는다 — 수정 전 실패까지 봐야 한다
- 실기기 항목을 maestro·jest 로 억지로 재지 않는다
- 자격증명을 플로우·레포·앱 `.env` 에 쓰지 않는다
