# 작업 문서 작성

기능 작업 루프의 첫 단계다. 여기서 정한 체크리스트와 검증 층이 그대로 `feature-verify`
의 작업 목록이 된다.

## 프로젝트 설정

프로젝트 루트의 `.feature-loop.json` 을 읽는다.

```json
{ "specsDir": "<작업 문서 폴더>", "testingGuide": "<테스트 기준 문서 — 선택>" }
```

- `specsDir` 가 없으면 사용자에게 묻고 파일을 만들자고 제안한다
- 폴더가 처음이면 `${CLAUDE_SKILL_DIR}/templates/specs-readme.md` 를 `<specsDir>/README.md` 로 둔다

## 입력

| 입력 | 필수 | 비고 |
|---|---|---|
| 시안 링크 | O | Figma 면 `node-id` 까지. 페이지·Section 링크 하나면 된다 |
| 기획 | - | 기획 문서와 시안의 흐름도·설명. 둘 다 있으면 같이 본다 |
| 티켓 | - | 있으면 적는다 |

시안이 없으면 받을 때까지 쓰지 않는다. 시안 없이 체크리스트를 지어내지 않는다.

## 절차

### 1. 읽는다 (Figma)

URL 의 `?node-id=1-2` 는 `1:2` 로 넘긴다. Dev Mode 링크는 그때 선택된 레이어를 가리키므로
`get_metadata` 로 받은 노드가 페이지·Section 인지 먼저 본다 — 인스턴스 하나면 링크를 다시 받는다.

1. `get_metadata` 로 구조를 받는다. 페이지 단위는 결과가 커서 파일로 저장되므로 거기서 뽑는다
   - Section 과 그 아래 화면 프레임 (이름·위치) — x 순서가 대체로 흐름 순서다
   - 연결선 — `vector` 이름이 `A --> B` 꼴이면 화면 간 이동이다
   - 흐름도·설명 텍스트 — 분기 조건이 여기 있다
2. 범위의 화면 프레임마다 `get_screenshot`. 페이지·Section 통째로 찍으면 글자를 못 읽는다
3. 이름이 같은 프레임이 여럿이면(버전·상태) 어느 것인지 **질문으로 모은다**

간격·색은 여기서 보지 않는다 — 구현과 시안 대조의 몫이다.

기획에서 조건(누구에게·언제 보이나)과 실패 경로를 뽑는다. 시안·기획·앱이 서로 다르면
**질문 목록으로 따로 모은다.** 어느 쪽이 맞는지 추측하지 않는다. 확인된 차이는 작업 문서의
유의사항에 남긴다.

### 2. 사용자 상태를 나눈다

체크리스트를 쓰기 전에 화면을 가르는 **상태 축**을 나열한다 — 로그인 여부, 구독·가입 여부,
등록 데이터 유무 등. 축마다 화면·이동이 어떻게 달라지는지 표로 적는다. 한 상태만 전제로 깔지 않는다.

```
| 상태 | 목록 화면 | 상세 CTA |
|---|---|---|
| 미로그인 | 안내 배너 | 로그인 화면 |
| 로그인·미구독 | 안내 배너 | 구독 화면 |
| 로그인·구독 | 메뉴 | 기능 화면 |
```

체크리스트는 **화면·동작이 실제로 달라지는 조합에만** 쓴다. 축이 늘면 조합이 곱으로 늘어나므로
모든 조합을 나열하지 않는다.

maestro 로 볼 상태마다 그 상태의 테스트 계정이 필요하다. 계정이 실제로 그 상태인지
확인하고, 없는 상태는 질문으로 올린다.

이미 구현된 기능을 문서로 옮길 때는 시안에 없는 조건을 앱 코드에서 확인할 수 있다.
그때는 **"코드 기준"** 이라고 표시한다. 새 기능에서는 코드를 근거로 쓰지 않는다 — 질문으로 올린다.

### 3. 쓴다

`${CLAUDE_SKILL_DIR}/templates/spec.md` 를 `<specsDir>/<기능-이름>.md` 로 복사해 채운다.
파일 이름은 티켓 번호가 아니라 기능 이름이다 — 문서는 기능 단위로 찾는다.

체크리스트는 **확인 가능한 문장만** 쓴다. 한 항목에 한 가지 동작.

- 보이는 것 — "목록 상단에 만료 D-day 배너가 보인다"
- 조건 — "이미 갱신했으면 배너가 보이지 않는다"
- 이동 — "배너를 누르면 갱신 화면으로 간다"
- 실패 경로 — "조회 실패 시 배너를 숨긴다"

### 4. 검증 층을 정한다

항목마다 층을 하나 고른다. `testingGuide` 가 있으면 그 기준을 따른다. 없으면 아래 표를 쓴다.

| 항목 성격 | 층 |
|---|---|
| 상태 전이·분기, 훅 생명주기, 순수 함수, 렌더 트리(무엇이 보이나) | jest |
| 실제 앱에서의 탭·화면 이동·네트워크를 거친 표시 | maestro |
| 애니메이션, 제스처, 특정 폭에서의 모양 | 실기기 |

같은 항목을 jest 와 maestro 가 둘 다 볼 수 있으면 **jest** 로 둔다. 더 빠르고 CI 에서 돈다.

maestro 행마다 **회귀 묶음에 넣을지** 함께 정한다 — 기능의 핵심 경로(로그인·결제·가입처럼
깨지면 사용자가 막히는 길)만 넣는다. 회귀 묶음은 마이그레이션 전후에 돌고 늘 통과해야 하므로
적게 시작해 필요할 때 늘린다.

**외부 연동을 일으키는 확정 동작은 maestro 로 누르지 않는다** — 결제·예약·호출·환불처럼
dev 에서도 외부 시스템에 요청이 나가는 것. maestro 는 확정 화면이 보이는 것까지, 확정 이후는
jest(API mock) 나 실기기 행으로 둔다.

경로는 레포에 남길 것만 적고 나머지는 `-` 다.
- jest — 프로젝트의 테스트를 남기는 기준에 해당할 때만(기준이 없으면 사용자에게 묻는다)
- maestro — 회귀 묶음만. `<appDir>/.maestro/<기능-이름>/<flow>.yaml`

### 5. 승인받는다

문서 경로와 함께 다음을 보고하고 **멈춘다.**

- 상태 축과 조합
- 체크리스트 항목 수와 층별 개수
- 질문 목록 (시안·기획 불일치, 빠진 상태)
- 범위 밖으로 둔 것

승인 전에는 구현도 테스트 작성도 하지 않는다. 체크리스트가 틀리면 테스트도 같이 틀린다.
수정 요청이 오면 문서를 고치고 다시 보고한다.

## 하지 않을 것

- 기획·시안 본문을 문서에 옮기지 않는다 — 링크가 정본이다
- 확인할 수 없는 문장("자연스럽다", "개선한다")을 체크리스트에 넣지 않는다
- 시안과 기획이 다를 때 한쪽을 골라 쓰지 않는다 — 질문으로 올린다
- 이번 실행의 사정(테스트 계정 상태, 보류 이유)을 작업 문서에 쓰지 않는다 — 문서는 기능의 스펙이다
