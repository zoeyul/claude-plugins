# 작업 문서

기능 하나당 파일 하나. 작업 **전에** 체크리스트를 적고 들어간다.

기획과 시안은 다른 곳에 있다. 여기엔 **이 레포가 무엇을 만족해야 하는지**만 적는다 —
링크로 잇고 본문을 복사하지 않는다. 복사하면 원본이 바뀌었을 때 어긋난다.

작업 문서는 그 기능의 스펙으로 계속 쓰인다. 기능의 요구와 검증 방법만 적고, 실행 사정
(테스트 계정 상태, 보류 이유)은 PR 에 적는다.

## 쓰는 법

**확인 가능한 문장만 적는다.** "사용성을 개선한다" 는 체크할 수 없다.
"만료 30일 전부터 목록에 배너가 보인다" 는 체크할 수 있다.

검증 표의 **층·경로가 검증 단계의 작업 목록이 된다.** 작업 전에 층을 정해두면
검증할 때 무엇을 jest 로 쓰고 무엇을 플로우로 쓸지 다시 판단하지 않는다.

## 시안이 정본이 아닐 때

기능이 추가·변경되면서 시안이 갱신되지 않거나, 기획 문구가 바뀌어 흐름도와 어긋날 수 있다.

- 시안·흐름도·앱이 서로 다르면 어느 쪽이 맞는지 정하지 않고 질문으로 올린다
- 확인된 차이는 작업 문서의 **유의사항**에 남긴다
- 기능을 바꾸면 시안·흐름도도 함께 갱신하고 이력을 남긴다

## 늘어나지 않게

- 체크리스트는 화면·동작이 달라지는 상태 조합에만 쓴다
- maestro 플로우는 검증할 때 다 돌리고, 레포에는 **회귀 묶음**에 넣을 핵심 경로만 남긴다
  (`tags: [regression]`). 반복되는 단계(로그인·출발점으로 되돌리기)는 `.maestro/common/`
- jest 테스트는 프로젝트의 테스트를 남기는 기준에 해당할 때만 레포에 남긴다
- 기능을 지우면 작업 문서·플로우도 같은 PR 에서 지운다

적게 시작하고 필요할 때 늘린다.

### 회귀 묶음

레포의 maestro 플로우는 늘 통과해야 한다. 마이그레이션·의존성 업데이트 전후와 배포 전에 돌린다.
깨지면 회귀이거나 플로우가 낡은 것이다 — 그 자리에서 고친다.

## 흐름

1. `feature-spec` — 시안·기획으로 이 문서를 쓴다. **사람 승인 후** 다음으로 간다
2. 구현 — 프로젝트에 시안 대조 스킬이 있으면 구현 직후 그것으로 자가 검수한다
3. `feature-verify` — 검증 표대로 jest·maestro 를 쓰고 돌려 체크박스를 채운다
